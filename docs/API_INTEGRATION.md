# API Integration

**Phase 12 status:** The review workspace can use an API-backed treatment
session for review, explicit editing, recalculation, adjunct proposal display,
and ZIP export. React only renders DTOs and sends explicit edit requests; all
treatment computation remains in existing Python engines.

## Local Development

Start the API from the repository root:

```bash
source services/api/.venv/bin/activate
PYTHONPATH=.:services/api uvicorn app.main:app --app-dir services/api --reload
```

Start the web app separately:

```bash
pnpm --filter @alignerstudio/web dev
```

Set `VITE_API_BASE_URL` when the API is not at `http://localhost:8000`.

## Data Modes

- **API engineering demo:** `POST /cases/demo` creates a complete, deterministic
  fixture session. It is marked `fixture: true` and is not a substitute for a
  scan, model, clinical review, or manufacturing data.
- **Uploaded case:** create, upload, and basic mesh validation use the API.
  A complete case requires one `upper` and one `lower` STL. Each arch is sent
  to `POST /cases/{case_id}/uploads?arch={upper|lower}` and may be removed with
  `DELETE /cases/{case_id}/uploads/{arch}`. The frontend enables Generate Plan
  only after both files validate. Plan generation returns `503` until a real
  segmentation model and the required identification pipeline are configured.
  No fixture/model fallback is used for uploads.
- **Local fixture preview:** remains available in the browser as an explicit
  engineering fallback. It cannot call the ZIP export endpoint.

## API Flow

```text
POST /cases/demo
  -> ReviewBundle
POST /cases/{case_id}/treatment/edits
  -> edited ReviewBundle
POST /cases/{case_id}/treatment/recalculate
  -> restaged/revalidated ReviewBundle
GET /cases/{case_id}/treatment/proposals
  -> review-only IPR and attachment sites
POST /cases/{case_id}/export
  -> ZIP, X-AlignerStudio-Manifest header
POST /cases/{case_id}/pipeline/{upper|lower}
  -> engineering diagnostic state and timing metrics
```

The export ZIP is generated by `TreatmentExportEngine`. The frontend preserves
the parsed manifest in its completion status and downloads the binary response.
All manifest provenance, fixture state, and warnings remain intact.

## Real-Case Processing

`POST /cases/{case_id}/pipeline/{arch}` never enters fixture mode. It returns
one of `model_unavailable`, `segmentation_failed`,
`identification_incomplete`, `planning_unavailable`, or `planning_ready`, with
engineering-only segmentation/total runtime, instance count, identification
counts/confidence, validation findings, and failures. A ready result means
geometry has reached the explicit-objective planning boundary; it does not
create objectives or claim clinical accuracy.

See [SEGMENTATION_ENGINE.md](SEGMENTATION_ENGINE.md) for the external artifact
and contract environment requirements.

## Excluded

This integration adds no clinical algorithm, ML model, authentication, cloud
deployment, patient sharing, DICOM, or manufacturing workflow.
